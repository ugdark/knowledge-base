# モダンAWS構築ガイド2026

## 概要

2026年時点のモダンなAWSアプリケーション構築ガイド。Kubernetes動向、Platform Engineering、サーバーレス・コンテナのハイブリッド構成、新規プロジェクトの標準スタックをまとめる。「ECS + Terraform」で止まっている知識のアップデート用。

---

## Kubernetes動向

### 健在どころか支配的

- **コンテナ利用者の82%がK8sを本番運用**（CNCF 2025、2023年は66%）
- 2026年には世界の90%以上の組織がコンテナ化アプリを本番運用予定
- **AI/MLワークロードのデファクト**（CNCF Kubernetes AI Conformance Program、2025年11月開始）

### K8s代替の状況

| ツール | 状況 |
|--------|------|
| **HashiCorp Nomad** | ニッチ。IBMも「K8sが勝った」と認識 |
| **Docker Swarm** | 2019年以降停滞。2026年にMirantisサポートで小さな復活 |
| **K3s** | エッジ・IoT向け軽量K8s。CNCFプロジェクト |

### WebAssembly（WASM）の位置づけ

- 2026年時点: **コンテナの置き換えではなく共存**
- WebAssembly 3.0がW3C標準化（2025年9月）、WASI 0.3.0は2026年2月予定
- エッジ・サーバーレス・プラグインシステム向けに強い
- 一般的なWebサービスでは「要ウォッチ、まだ採用段階ではない」

## Platform Engineering（新しいDevOps）

- **55%の組織がPlatform Engineeringを採用**（2025年）
- 「各チームがK8sを管理」ではなく、プラットフォームチームが**IDP（Internal Developer Platform）**を構築
- 開発者は抽象化されたインターフェースを使う

### 主要ツール

- **Backstage**（Spotify） — サービスカタログ・ポータル
- **Crossplane** — K8s上でクラウドリソースを宣言的に管理
- **Kratix** — プラットフォームAPIの抽象化
- **Port** — 開発者ポータル

### ECS中心のチームでも応用可能

K8sを使わなくても、以下の標準化でIDP相当は作れる:
- 標準化されたECSタスク定義テンプレート
- サービスモジュール（Terraform/OpenTofu）
- CI/CDパイプラインテンプレート

| サービス | 特徴 |
|---------|------|
| **AWS Fargate** | 最も成熟、最安 |

**78%のチームがサーバーレス＋コンテナのハイブリッド構成**を採用。

## 「ECS + Terraform」から追いつくべきポイント

### パラダイムシフト（2020以降）

1. **IBMがHashiCorp買収（2025年2月）** — Terraform知識は有効だが、BSLとOpenTofu代替を把握しておく。**CDKTFは死亡**
2. **ECS Managed Instances（2025年9月）** — EC2とFargateの中間の第3選択肢。ECS以来最大の変更
3. **Platform Engineeringが新DevOps** — 各チームがK8s管理するのではなく、IDPで抽象化
4. **サーバーレスコンテナが主流** — 78%のチームがハイブリッド構成
5. **セキュリティ標準化** — rootless・SBOM・イメージ署名が前提に
6. **AI/MLインフラ** — Bedrock、SageMaker、Trainium/Inferentiaが新カテゴリ

### 実践的な推奨

- **ECS + Terraformスキルは今も有効**。陳腐化していない
- **ECS Managed Instancesを評価**: Fargateから切り替えでコスト30-50%削減の可能性
- **App Runnerを評価**: シンプルなHTTPサービスならECSのボイラープレート不要に
- **OpenTofu検討**: BSLが気になるならシームレスに移行可能
- **GitHub Actions移行**: まだならCI/CDはこれ

## 2026年のAWS新規プロジェクト標準スタック

| レイヤ | 推奨 | 備考 |
|--------|------|------|
| **コンピュート** | ECS Fargate or Managed Instances | シンプルなHTTPならApp Runner |
| **IaC** | OpenTofu or Terraform | terraform-aws-modulesを活用 |
| **CI/CD** | GitHub Actions | エンタープライズならGitLab CI |
| **コンテナビルド** | Docker（開発）/ multi-stage | CIでPodman（rootless） |
| **ネットワーク** | ALB + VPC（マルチAZ） | |
| **監視** | CloudWatch or Datadog/Grafana | OpenTelemetryが標準 |
| **セキュリティ** | ECRスキャン + Trivy + SBOM | |
| **シークレット** | Secrets Manager / Parameter Store | マルチクラウドならVault |

## 判断フロー

### コンピュート選択

```
シンプルなHTTP API → App Runner
イベント駆動・短時間 → Lambda
コンテナで普通に → ECS + Fargate
コンテナでコスト重視 → ECS + Managed Instances
K8sが必要 → EKS
```

### IaC選択

```
ライセンスリスク回避 → OpenTofu
最大エコシステム優先 → Terraform
プログラミング言語で書きたい → Pulumi
AWS専業で統合重視 → AWS CDK
```
