# 認証方式選択ガイド（統合版）

## 概要

Web認証の実装方式を選択するための実践的ガイド。Session方式とToken方式（JWT）の特徴を理解し、プロジェクト要件に最適な方式を選択できるようにすることを目的とする。対象読者はWebアプリケーション開発者、アーキテクト、技術リード。

---

## 2. 主要な認証方式

### 2.1 Session方式（Stateful）

**概要**:
- サーバー側でセッション状態を管理する認証方式
- クライアントにはセッションIDのみを保存
- ユーザー情報はサーバー側のストレージ（Redis、DB等）に保存

**仕組み**:
1. ログイン成功時、サーバーがランダムなセッションIDを生成
2. セッションIDをCookieでクライアントに送信
3. セッションデータ（ユーザー情報等）をサーバー側に保存
4. 以降のリクエストでセッションIDを検証し、セッションデータを取得

**特徴**:
- セッションを即座に無効化できる
- サーバー側でセッション管理が必要（Stateful）
- 各リクエストでストレージアクセスが発生

**参考**: OWASP Session Management Cheat Sheet

### 2.2 Token方式（Stateless / JWT）

**概要**:
- トークン自体にユーザー情報を含める認証方式
- サーバー側でセッション保存が不要（Stateless）
- JWTが最も一般的な実装

**仕組み**:
1. ログイン成功時、ユーザー情報を含むJWTを生成
2. JWTをクライアントに送信（CookieまたはレスポンスBody）
3. 以降のリクエストでJWTを受け取り、署名を検証
4. JWTからユーザー情報を取り出して使用（DBアクセス不要）

**特徴**:
- サーバー側でセッション保存が不要（Stateless）
- スケーリングが容易（各サーバーが独立して検証可能）
- 即座に無効化できない（有効期限まで有効）

**参考**: RFC 7519 (JSON Web Token)

## 3. JWTを使う場合のパターン

### 3.1 Access Token + Refresh Token

**概要**:
- 短期トークン（Access Token）と長期トークン（Refresh Token）を組み合わせる方式
- OAuth 2.0で定義されている標準パターン

**仕組み**:
1. ログイン時に2種類のトークンを発行
   - Access Token: 短期（5-15分）、API呼び出しに使用
   - Refresh Token: 長期（7-30日）、Access Token再発行に使用
2. APIリクエストはAccess Tokenで認証
3. Access Token期限切れ時、Refresh Tokenで新しいAccess Tokenを取得
4. Refresh Token期限切れ時、再ログインが必要

**特徴**:
- セキュリティが高い（短期トークンで漏洩リスク低減）
- Refresh TokenをDB管理すれば無効化可能
- 実装が複雑（2種類のトークン管理が必要）

**参考**: RFC 6749 (OAuth 2.0)

### 3.2 Single Token

**概要**:
- 1種類のJWTのみを使用するシンプルな方式
- Access TokenとRefresh Tokenを区別しない

**仕組み**:
1. ログイン時に1つのJWTを発行
2. 全てのAPIリクエストでそのJWTを使用
3. トークン期限切れ時、再ログインが必要

**特徴**:
- 実装がシンプル
- トークン管理が容易
- 有効期限の設定が難しい（短すぎるとUX悪化、長すぎるとセキュリティリスク）

## 4. 有効期限の管理

### 4.1 固定期限（Fixed Expiration）

**概要**:
- トークン発行時に決めた有効期限が変更されない方式
- アクセスしても期限は延長されない

**仕組み**:
1. トークン発行時に有効期限を設定（例：発行から24時間後）
2. ユーザーがアクセスしても期限は変わらない
3. 設定した期限が来たら失効

**特徴**:
- セキュリティが高い（絶対的な有効期限がある）
- トークン盗難時の影響を限定できる
- 使用中でも期限が来たら再ログインが必要

### 4.2 延長期限（Sliding Expiration）

**概要**:
- ユーザーがアクセスするたびに有効期限を延長する方式
- 使い続ける限り失効しない

**仕組み**:
1. トークン発行時に有効期限を設定（例：30日）
2. ユーザーがアクセスするたびに「現在時刻 + 30日」に更新
3. 使い続ける限り永久に有効

**特徴**:
- ユーザー体験が良い（使用中に突然ログアウトしない）
- 使い続ける限り永久に有効（セキュリティリスク）
- トークン盗難時、犯人も使い続ける限り有効

## 5. 組み合わせパターンと選択基準

### 5.1 一般的な組み合わせ

以下は実際によく使われる組み合わせパターンです。

**パターン1: Session + Fixed**
- 構成: Session方式 + 固定期限
- 適用例: 単一Webアプリケーション、高セキュリティ要件
- 特徴: シンプルで安全、即座に無効化可能

**パターン2: Session + Sliding**
- 構成: Session方式 + 延長期限
- 適用例: 社内ツール、長時間作業が想定されるアプリ
- 特徴: ユーザー体験が良い、即座に無効化可能

**パターン3: JWT (Dual Token) + Fixed**
- 構成: Access Token + Refresh Token + 固定期限
- 適用例: マイクロサービス、モバイルアプリ + API
- 特徴: スケーラブル、セキュリティが高い

**パターン4: JWT (Single Token) + Fixed**
- 構成: 単一JWT + 固定期限
- 適用例: シンプルなAPI、短期トークン（1時間以内）
- 特徴: 実装が簡単、短期利用向け

### 5.2 決定フローチャート

```
Q1: マイクロサービス or API中心のアーキテクチャか？
    ├─ YES → Q2へ
    └─ NO  → Session方式を選択

Q2: 高セキュリティ要件（短期トークン必須）か？
    ├─ YES → JWT (Dual Token) + Fixed
    └─ NO  → JWT (Single Token) + Fixed

Q3: (Session方式の場合) ユーザー体験を優先するか？
    ├─ YES → Session + Sliding
    └─ NO  → Session + Fixed
```

## 6. セキュリティベストプラクティス（OWASP準拠）

### Cookie属性（必須設定）

認証トークンをCookieで管理する場合、以下の属性は必須です。

**HttpOnly**:
- JavaScriptからのアクセスを防ぐ
- XSS攻撃によるトークン盗難を防止

**Secure**:
- HTTPS通信のみでCookieを送信
- 通信傍受によるトークン盗難を防止

**SameSite**:
- CSRF攻撃を防止
- 値: `Strict` または `Lax`（認証Cookieは `Strict` を推奨）

**設定例**:
```http
Set-Cookie: sessionId=value;
  HttpOnly;
  Secure;
  SameSite=Strict;
  Max-Age=86400;
```

### トークン格納場所

| 格納場所 | 評価 | 理由 |
|---------|------|------|
| HttpOnly Cookie | 推奨 | JavaScriptからアクセス不可、XSS対策 |
| localStorage | 非推奨 | XSS攻撃で容易に盗まれる |
| sessionStorage | 非推奨 | XSS攻撃で容易に盗まれる |

### 有効期限の目安

一般的な設定値（業界慣習）:

| トークン種別 | 推奨期限 |
|------------|---------|
| Access Token | 5-15分 |
| Refresh Token | 7-30日 |
| Session Cookie | 1-24時間 |

**参考**: OWASP Session Management Cheat Sheet

## 7. 実装チェックリスト

### 全パターン共通

- [ ] HTTPS必須（本番環境）
- [ ] HttpOnly属性を設定
- [ ] Secure属性を設定
- [ ] SameSite属性を設定（Strict推奨）
- [ ] 適切な有効期限を設定

### Session方式

- [ ] セッションストレージを用意（Redis等）
- [ ] セッションタイムアウトを設定
- [ ] ログアウト時にセッションを削除
- [ ] セッション固定攻撃対策（ログイン時にID再生成）
- [ ] 複数サーバー間でセッション共有の仕組み

### JWT方式

- [ ] 強力な署名アルゴリズム使用（HS256以上、推奨RS256）
- [ ] JWTに機密情報を含めない（Base64は暗号化ではない）
- [ ] Access Tokenを短期に設定（5-15分）
- [ ] Refresh TokenをDB管理（無効化可能にする）
- [ ] Refresh Token Rotation実装（再利用攻撃対策）
