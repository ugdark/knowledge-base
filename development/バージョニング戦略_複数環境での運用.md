# バージョニング戦略 - 複数環境での運用

## 概要

develop/staging/production環境ごとに異なるライブラリバージョンを使い分ける運用パターンを解説する。環境変数による動的切り替え、バージョンカタログ集約、ブランチ名による自動判定の各パターンと、SNAPSHOT版の更新管理をまとめる。

---

## 課題: 環境ごとに異なるバージョンを使いたい

### ユースケース

```
develop ブランチ  → dev環境にデプロイ     → ライブラリ開発版を使用
stage ブランチ    → stage環境にデプロイ   → ライブラリRC版を使用
production ブランチ → prod環境にデプロイ   → ライブラリ安定版を使用
```

**問題**: 各環境で適切なライブラリバージョンをどう管理するか？

---

## 運用パターン比較

### パターン1: 固定バージョン + 手動切り替え（非推奨）

```scala
// develop用のbuild.sbt
libraryDependencies += "org.example" %% "library" % "1.0.0-SNAPSHOT"

// production用のbuild.sbt
libraryDependencies += "org.example" %% "library" % "1.0.0"
```

**デメリット**:
- ブランチごとにbuild.sbtを手動変更
- マージ時にコンフリクト
- ヒューマンエラーのリスク

---

### パターン2: 環境変数で動的切り替え（推奨）

#### ライブラリ公開側の戦略

```
develop ブランチ  → 1.0.0-SNAPSHOT を GitHub Packages に公開
stage ブランチ    → 1.0.0-RC1 を GitHub Packages に公開
main ブランチ     → 1.0.0 を GitHub Packages に公開
```

#### 利用側の実装

**build.sbt**:

```scala
val libraryVersion = sys.env.get("ENV") match {
  case Some("production") => "1.0.0"          // prod環境
  case Some("staging")    => "1.0.0-RC1"      // stage環境
  case _                  => "1.0.0-SNAPSHOT" // dev環境（デフォルト）
}

libraryDependencies += "org.example" %% "library" % libraryVersion
```

**CI/CD (GitHub Actions)**:

```yaml
# dev環境へのデプロイ
- name: Deploy to dev
  run: sbt deploy
  env:
    ENV: dev

# stage環境へのデプロイ
- name: Deploy to staging
  run: sbt deploy
  env:
    ENV: staging

# prod環境へのデプロイ
- name: Deploy to production
  run: sbt deploy
  env:
    ENV: production
```

**メリット**:
- build.sbtを変更不要
- 環境変数だけで制御
- マージ時のコンフリクトなし

---

### パターン3: バージョンカタログ集約（最推奨）

**project/Dependencies.scala**:

```scala
object Dependencies {

  object Versions {
    // 環境別バージョン定義
    object ExampleLibrary {
      val production = "1.0.0"
      val staging    = "1.0.0-RC1"
      val develop    = "1.0.0-SNAPSHOT"

      // 現在の環境に応じて選択
      def current: String = sys.env.get("ENV") match {
        case Some("production") => production
        case Some("staging")    => staging
        case _                  => develop
      }
    }

    object AnotherLibrary {
      val production = "2.1.0"
      val staging    = "2.1.0-RC2"
      val develop    = "2.1.0-SNAPSHOT"

      def current: String = sys.env.get("ENV") match {
        case Some("production") => production
        case Some("staging")    => staging
        case _                  => develop
      }
    }
  }

  // ライブラリ定義
  val exampleLibrary = "org.example" %% "example-library" % Versions.ExampleLibrary.current
  val anotherLibrary = "org.example" %% "another-library" % Versions.AnotherLibrary.current
}
```

**build.sbt**:

```scala
libraryDependencies ++= Seq(
  Dependencies.exampleLibrary,
  Dependencies.anotherLibrary
)
```

**メリット**:
- バージョン管理が一箇所に集約
- 複数ライブラリの管理が容易
- 変更時の影響範囲が明確

---

### パターン4: ブランチ名で自動判定（応用）

```scala
val currentBranch = sys.env.get("GITHUB_REF") match {
  case Some(ref) if ref.contains("refs/heads/main")    => "production"
  case Some(ref) if ref.contains("refs/heads/stage")   => "staging"
  case Some(ref) if ref.contains("refs/heads/develop") => "develop"
  case _                                               => "develop"
}

val libraryVersion = currentBranch match {
  case "production" => "1.0.0"
  case "staging"    => "1.0.0-RC1"
  case "develop"    => "1.0.0-SNAPSHOT"
}

libraryDependencies += "org.example" %% "library" % libraryVersion
```

**メリット**:
- 環境変数設定不要
- ブランチから自動判定

**デメリット**:
- ローカル開発時に環境変数が必要な場合がある

## 運用例: 具体的なフロー

### 前提

- **ライブラリリポジトリ**: `example-library`
- **アプリケーションリポジトリ**: `example-app`

### ステップ1: ライブラリ側のCI/CD設定

**.github/workflows/publish.yml (ライブラリ側)**:

```yaml
name: Publish Library

on:
  push:
    branches:
      - develop
      - stage
      - main

jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      packages: write

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: 'temurin'
          java-version: '21'
          cache: 'sbt'

      # バージョンをブランチに応じて設定
      - name: Set version
        run: |
          if [ "${{ github.ref }}" == "refs/heads/main" ]; then
            echo "VERSION=1.0.0" >> $GITHUB_ENV
          elif [ "${{ github.ref }}" == "refs/heads/stage" ]; then
            echo "VERSION=1.0.0-RC1" >> $GITHUB_ENV
          else
            echo "VERSION=1.0.0-SNAPSHOT" >> $GITHUB_ENV
          fi

      - name: Publish
        run: sbt "set version := \"$VERSION\"" publish
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

**結果**:
- `develop` → `1.0.0-SNAPSHOT`
- `stage` → `1.0.0-RC1`
- `main` → `1.0.0`

---

### ステップ2: アプリケーション側の設定

**project/Dependencies.scala (アプリ側)**:

```scala
object Dependencies {
  object Versions {
    object ExampleLibrary {
      val production = "1.0.0"
      val staging    = "1.0.0-RC1"
      val develop    = "1.0.0-SNAPSHOT"

      def current: String = sys.env.getOrElse("ENV", "develop") match {
        case "production" => production
        case "staging"    => staging
        case _            => develop
      }
    }
  }

  val exampleLibrary = "org.example" %% "example-library" % Versions.ExampleLibrary.current
}
```

**.github/workflows/deploy.yml (アプリ側)**:

```yaml
name: Deploy

on:
  push:
    branches:
      - develop
      - stage
      - main

jobs:
  deploy-dev:
    if: github.ref == 'refs/heads/develop'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to dev
        run: sbt deploy
        env:
          ENV: develop

  deploy-staging:
    if: github.ref == 'refs/heads/stage'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to staging
        run: sbt deploy
        env:
          ENV: staging

  deploy-production:
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to production
        run: sbt deploy
        env:
          ENV: production
```

## SNAPSHOT版の更新タイミング

### 問題: developで常に最新のSNAPSHOTを使いたい

#### 解決策1: CI/CDで毎回更新（推奨）

```yaml
- name: Update dependencies
  run: sbt clean update

- name: Build
  run: sbt compile
```

**メリット**: 常に最新のSNAPSHOT
**デメリット**: ビルド時間が増加

#### 解決策2: キャッシュを活用しつつ定期更新

```yaml
- uses: actions/cache@v3
  with:
    path: |
      ~/.ivy2/cache
      ~/.sbt
    key: ${{ runner.os }}-sbt-${{ hashFiles('**/build.sbt') }}

- name: Update SNAPSHOTs
  run: sbt "reload" "update"
  if: github.event_name == 'schedule' # 定期実行時のみ更新
```

#### 解決策3: 手動更新（開発環境）

```bash
# ローカル開発時
sbt clean update
```

## バージョン命名規則

### 推奨パターン

| 環境 | バージョン形式 | 例 | 用途 |
|------|---------------|-----|------|
| **develop** | `x.y.z-SNAPSHOT` | `1.0.0-SNAPSHOT` | 開発中の不安定版 |
| **staging** | `x.y.z-RC<n>` | `1.0.0-RC1` | リリース候補 |
| **production** | `x.y.z` | `1.0.0` | 本番用の安定版 |

### 代替パターン

| 環境 | バージョン形式 | 例 |
|------|---------------|-----|
| **develop** | `x.y.z-dev-SNAPSHOT` | `1.0.0-dev-SNAPSHOT` |
| **staging** | `x.y.z-staging-SNAPSHOT` | `1.0.0-staging-SNAPSHOT` |
| **production** | `x.y.z` | `1.0.0` |

## トラブルシューティング

### 問題1: stagingで古いSNAPSHOTが使われる

**原因**: キャッシュされた古いSNAPSHOT

**解決策**:

```bash
# キャッシュをクリア
rm -rf ~/.ivy2/cache/org.example/
sbt update
```

### 問題2: 環境変数が正しく設定されない

**原因**: CI/CDで環境変数が伝播していない

**解決策**:

```yaml
# 全ステップで環境変数を設定
env:
  ENV: production

steps:
  - name: Build
    run: sbt compile
    # envは自動的に継承される
```

### 問題3: ローカル開発でprod版が使われる

**原因**: `ENV`環境変数が未設定

**解決策**:

```scala
// デフォルトをdevelopに
def current: String = sys.env.getOrElse("ENV", "develop") match {
  case "production" => production
  case "staging"    => staging
  case _            => develop  // デフォルト
}
```

## まとめ

### 推奨構成

```
ライブラリ側:
  develop → 1.0.0-SNAPSHOT を自動公開
  stage   → 1.0.0-RC1 を自動公開
  main    → 1.0.0 を自動公開

アプリ側:
  project/Dependencies.scala でバージョン管理
  環境変数 ENV で切り替え
  CI/CDで環境に応じて自動設定
```

### ベストプラクティス

1. **バージョンを一箇所に集約** (Dependencies.scala)
2. **環境変数で制御** (build.sbt変更不要)
3. **CI/CDで自動化** (手動操作なし)
4. **SNAPSHOT更新を明示的に** (予期しない変更を防ぐ)
5. **本番は固定バージョン** (再現性確保)
