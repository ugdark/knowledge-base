# バージョニング戦略

## 概要

ライブラリ・Webサービスのバージョニング戦略を調査・比較する。セマンティックバージョニング（SemVer）、カレンダーバージョニング（CalVer）、継続的バージョニング、SNAPSHOT版運用などの各戦略と、Maven/sbtでの実務的な運用方法をまとめる。

---

## バージョニング戦略 比較表

| 戦略名 | 形式 | 採用事例 | 推奨用途 | 出典 |
|--------|------|----------|----------|------|
| **セマンティックバージョニング (SemVer)** | `MAJOR.MINOR.PATCH`<br>例: `1.2.3` | npm, Maven, Cargo, PyPI, RubyGems, NuGet | ライブラリ・パッケージ<br>（"ゴールドスタンダード"） | semver.org,<br>SensioLabs (2025) |
| **カレンダーバージョニング (CalVer)** | `YYYY.MM.DD`<br>例: `2026.2.3` | Ubuntu, Docker, pip | アプリケーション・内部ソフトウェア | SensioLabs (2025),<br>Wikipedia |
| **継続的バージョニング (CV)** | 日付・時刻・ブランチ・コミット・ビルド番号<br>例: `20260203-abc1234` | - | CD環境での高速デプロイ・履歴トラッキング | LinkedIn |
| **ハイブリッドバージョニング (HV)** | SemVer + CV<br>例: `1.0.0-20260203-abc1234` | - | 互換性管理とトレーサビリティの両立 | LinkedIn |
| **SNAPSHOT版 (Maven/sbt)** | `MAJOR.MINOR.PATCH-SNAPSHOT`<br>例: `1.0.0-SNAPSHOT` | Maven, sbt | 開発中の不安定バージョン | Oracle Maven Docs,<br>GitHub (2020) |

## 1. セマンティックバージョニング (SemVer)

### 概要

**公式仕様**: [semver.org](https://semver.org/)

**形式**: `MAJOR.MINOR.PATCH` (例: 1.2.3)

**ルール**:
- MAJOR: 後方互換性のない変更
- MINOR: 後方互換性のある機能追加
- PATCH: バグ修正

### 採用状況

**出典**: npm Docs, Maven Documentation, Baeldung, AWS DevOps Blog (2025)

以下のパッケージマネージャーで採用されている：
- npm (Node.js)
- Maven (Java)
- Cargo (Rust)
- PyPI (Python)
- RubyGems (Ruby)
- NuGet (.NET)

### 業界評価

**出典**: SensioLabs Blog (2025年1月), WorkOS Blog (2025年4月)

> "SemVer is the gold standard for libraries and packages"
>
> "ライブラリ・パッケージのゴールドスタンダード"

**理由**:
- 互換性と安定性を保証
- 依存プロジェクトにとって予測可能

### 要件

**出典**: semver.org公式仕様

- 公開APIの定義が必須
- API仕様は正確かつ包括的であるべき

## 2. カレンダーバージョニング (CalVer)

### 概要

**形式**: 日付ベースのバージョニング

**例**:
- `YYYY.MM.DD` (例: 2026.2.3)
- `YY.MM.MICRO` (例: 26.2.1)

### 採用事例

**出典**: Wikipedia Software Versioning, SensioLabs Blog (2025)

- Ubuntu: `20.04`, `22.04`
- Docker: `20.10.7`
- pip (Python): `21.0.1`

### 推奨用途

**出典**: SensioLabs Blog (2025年1月)

> "CalVer is the better choice for applications and internal software"
>
> "アプリケーションと内部ソフトウェアにはCalVerが良い選択"

## 3. 継続的デリバリー (CD) 環境でのバージョニング

### 3つの戦略

**出典**: LinkedIn "Versioning Strategies and Best Practices for Continuous Delivery"

#### 戦略1: セマンティックバージョニング

```
MAJOR.MINOR.PATCH
```

**メリット**:
- 各バージョンで何が変わったかを明確に伝えられる
- アップグレード・ダウングレードの影響を予測可能

#### 戦略2: 継続的バージョニング (Continuous Versioning)

```
日付・時刻・ブランチ・コミット・ビルド番号などで生成
```

**メリット**:
- 履歴のトラッキングに有用
- CD環境での高速デプロイに対応

#### 戦略3: ハイブリッドバージョニング

```
セマンティック + 継続的の組み合わせ
```

**メリット**:
- 互換性維持とトレーサビリティの両立
- CD環境での自動化・追跡性をサポート

### ベストプラクティス

**出典**: LinkedIn, Xebia Blog, Medium

1. **自動化**
   - Git、Maven、Gradle、Jenkinsなどのツールを活用
   - コミットメッセージやリリースノートからバージョンを自動インクリメント

2. **フィーチャーフラグ**
   - サービスのデプロイと機能リリースを分離
   - 継続的デプロイを可能にしつつ、機能は準備完了まで非公開

3. **ドキュメント化**
   - バージョニングポリシーを明確に文書化
   - CHANGELOGやリリースノートで変更を伝達

## 4. Maven/sbtでの運用

### SNAPSHOT vs Release

**出典**: Oracle Maven Documentation, Baeldung, Reintech

#### SNAPSHOT版

```
1.0.0-SNAPSHOT
```

**特徴**:
- 開発中の不安定バージョン
- 同じバージョン番号で上書き可能
- タイムスタンプ付きで複数SNAPSHOTが共存

**GitHub Packages対応**:
**出典**: GitHub Changelog (2020年3月10日)

> "Packages supports snapshots for Apache Maven"

2020年から正式にSNAPSHOT版をサポート

#### Release版

```
1.0.0
```

**特徴**:
- 本番環境用の安定版
- イミュータブル（変更不可）
- 無期限に保持される

### 高頻度リリースの運用

**出典**: MoldStud "Best Practices for Versioning Java Projects with Maven"

#### 問題

> "Because a single artifact can be deployed multiple times in a day, repository instances can increase rapidly"
>
> "1日に複数回デプロイされるため、リポジトリインスタンスが急増する"

#### 推奨アプローチ

**日次・週次リリースの場合**:

```
タイムスタンプやビルド番号を組み込む
例: 1.3.0-20241101-001
```

**理由**:
- リリース版を常に作り続けるのは管理不可能
- SNAPSHOT版はリポジトリマネージャーが古いものを自動削除するため、ストレージ要件が一定に保たれる

### 自動化ツール

**出典**: MoldStud, Baeldung

#### maven-release-plugin

**効果**:
- バージョン更新の自動化
- 時間削減50%
- 人的エラーの排除

**推奨事項**:
- セマンティックバージョニング原則の遵守
- Git Flowのようなブランチ戦略との組み合わせ
