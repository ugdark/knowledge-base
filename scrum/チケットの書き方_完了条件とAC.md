# チケットの書き方（完了条件とAC）

## 概要

issue・ユーザーストーリー・バックログアイテムを書く時のルールと、その根拠。過去のスクラム導入・運用で実践してきたメモから「なぜそう書くのか」を含めて整理した。

---

## 1. チケットの基本形

```markdown
## 目的
<なぜやるのか。背景と狙いを1〜3文>

## やること
<作業内容の箇条書き>

## 完了条件（AC）
- [ ] <OK/NGが判定できる条件>

## スコープ外
- <このチケットでやらないこと>
```

## 2. ルールとその理由

### 目的と完了条件をしっかり書く

**Why**: スクラムは「チームの問題を早期発見するための手法」であり、その土台は透明性 = 正しい情報が1箇所に集められ、次の行動が誘発され続けている状態。目的と完了条件が本文だけで分かるチケットは、この透明性の最小単位になる。

また「完了」の定義は人によって異なる。チケットに完了条件を明記するのは認識相違の防止のためで、Working Agreement で「完了の定義をきっちり定める」と合意していたのと同じ理屈をチケット単位に適用したもの。

### 完了条件（AC）は必ず1つ以上、OK/NGが判定できる文で書く

**Why**: **AC = 受け入れ条件 = 検証**。ACとはソリューションに対しての検証方法であり、検証できない条件はACとして成立しない。バックログアイテム1つに対して必ず1つ以上定義する。ACは「開発したプロダクトがユーザーやクライアントに受け入れてもらえるか」をチームが考える機会を与えるために存在する。

効果的なACの3特徴:

1. OK/NG が明確に定義されている
2. 簡潔で、明確である
3. チームでの共通理解に基づいている

ACを書いたら次を自問する:

- この条件は誰にとっての価値提供か？
- いくつの条件を必要とするのか？
- 結果をどのように測定するのか？
- 上限（どこまでやるか）をどこに置くか？

ACは解決策ではなく意思（何を満たすべきか）を述べる。POとチームの協働で定義するもので、一方的に押し付けるものではない。

### フォーマットは規則指向 or シナリオ指向（Given/When/Then）の2択

**Why**: ACのフォーマットは規則指向（条件の箇条書き）とシナリオ指向（BDD由来の Given/When/Then）のどちらかに寄る傾向がある。振る舞いに注目するチケットはシナリオ指向が向く。

「正しい」フォーマットは存在せず、効果は協業性で決まる。ただし最初はテンプレートを使う方が安全な構造（安定したプロセス）を提供できる。テンプレートが思考停止や協業性の低下につながらないよう注意する。

### スコープ外（やらないこと）を書く

**Why**: 「やってはいけないことを記載するのもテクニックの1つ」。期待の膨張とスコープクリープを防ぎ、レビュー時の「これもやってくれると思った」を潰す。

### 8時間以内で終わる粒度にする

**Why**: ストーリーポイントを使わず「8時間以内で終わる粒度に分割する」運用にしていた。粒度を固定すると見積り技術が不要になり、デイリーで進捗の異常（1日で終わるはずが終わらない）を機械的に検出できる。超えそうなら分割する。

## 3. DoneとACの違い

| | Done（完了の定義） | AC（受け入れ条件） |
|---|---|---|
| 視点 | 作り手側。リリースを見据えて定義 | 受け入れ側。ユーザー・クライアントに受け入れられるか |
| 単位 | チーム共通（全チケットに適用） | チケットごとに個別定義 |
| 決め方 | Working Agreement として全員で合意 | POとチームの協働 |

チケットに書くのはAC。Doneはチーム共通ルールなので個々のチケットには書かない。

### Done定義のテンプレート

どこまでをストーリーの完了に含めるかをチームで決める。含めたものがDone、含めなかったものがUnDone。

| No | 内容 | Done? |
|---|---|---|
| 1 | 単体テスト通過 | |
| 2 | 結合テスト通過 | |
| 3 | プルリクの承認 | |
| 4 | レビュー | |
| 5 | 総合テスト | |
| 6 | 負荷テスト | |
| 7 | セキュリティテスト | |
| 8 | デプロイ | |

**UnDoneは負債**。プロジェクトが進むにつれ作業の効率を妨げるので、UnDoneを減らす作業（デプロイ自動化等）自体をストーリーにする。

## 4. ACを考えるタイミング

プランニング・リファインメントでは「ソリューションを出す → ACを考える」の順で時間を確保していた。AC = 検証方法なので、解決策が決まった直後に検証を定義するのが自然な流れ。実装を始めてからACを後付けすると、検証しやすい形に条件が歪む。
