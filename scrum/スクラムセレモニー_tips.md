# スクラムセレモニー Tips

## 概要

スクラムに関する補足的な用語やTipsをまとめたドキュメント。スパイク、タイムボックス、ベロシティの3つの概念を中心に、実践的な使い方と注意点を解説する。
基本的なセレモニーについては `スクラムセレモニー.md` を参照。

---

## スパイク (Spike)

### 概要
調査や技術検証など、見積もりが難しい不確実な作業に対して使う手法。

### 特徴

1. **タイムボックス**
   - 調査時間に上限を設定する
   - 例：2日、1スプリント、4時間など
   - 無制限に調査時間を使わないための制約

2. **目的**
   - 不確実性を減らす
   - 本実装の見積もりを可能にする
   - 技術的実現可能性の確認

3. **成果物**
   - コードではなく、知識や調査結果のドキュメント
   - 技術的な判断材料
   - 見積もりの根拠

4. **判断基準**
   - 「実装可能か」を明確にする
   - 「どのくらいかかりそうか」を見積もれるようにする
   - リスクの洗い出し

### 使用例

```
調査スパイク: 「外部APIとの連携方法調査」（2日のタイムボックス）
↓ 調査結果をもとに
実装タスク: 「外部API連携機能実装」（5日）← 見積もり精度向上
```

### 適用場面

- 新しい技術スタックの導入検討
- パフォーマンス改善の調査
- 外部サービスとの連携可能性確認
- アーキテクチャの大幅変更の事前調査
- セキュリティ対策の方法検討

### スパイクのアウトプット例

```markdown
## スパイク結果レポート: 外部API連携方法調査

### 調査期間
2日間（2026-01-20 〜 2026-01-21）

### 結論
✅ 実装可能
見積もり: 5日間（実装3日 + テスト2日）

### 検証内容
1. API仕様の確認
2. 認証方法の検証（OAuth 2.0）
3. レート制限の確認（100req/min）
4. エラーハンドリングのパターン

### 技術的リスク
- レート制限に注意（リトライ処理必須）
- トークン更新ロジックが必要

### 推奨アプローチ
OAuth 2.0ライブラリを使用し、トークン管理は既存の認証基盤を流用
```

## タイムボックス (Time-box)

### 概要
作業や会議に対して、最初から時間枠を固定して区切る考え方。
スクラム全般で使われる重要な概念。

### タイムボックスが適用される場面

1. **スプリント自体**
   - 期間固定（2週間など）
   - 延長は認めない
   - スクラムの基本単位

2. **デイリースクラム**
   - 15分以内（厳守）
   - 時間が来たら強制終了
   - 詳細議論は別途実施

3. **スプリントプランニング**
   - 2〜8時間（スプリント長に応じて）
   - 時間内に計画を完了させる

4. **スプリントレビュー**
   - 1〜4時間
   - デモとフィードバックに集中

5. **スプリントレトロスペクティブ**
   - 1〜3時間
   - アクションアイテム決定まで完了

6. **スパイク（調査作業）**
   - 調査時間の上限を設定
   - 無制限な調査を防ぐ

### タイムボックスの効果

```
メリット:
✅ ダラダラとした会議を防ぐ
✅ 集中力を維持できる
✅ 優先順位が明確になる
✅ 「時間内に終わらせる」意識が高まる
✅ 予定が組みやすくなる

デメリット:
❌ 時間が足りない場合がある
❌ 議論が深まりにくい場合がある
→ 別途フォローアップを設定すればOK
```

### タイムボックスの運用ポイント

1. **時間厳守**
   - アラームやタイマーを使う
   - ファシリテーターが時間管理

2. **詳細議論は別途**
   - タイムボックス内で完結させようとしない
   - 「後で議論する」を明確にする

3. **事前準備を徹底**
   - アジェンダを共有
   - 必要な資料を用意
   - タイムボックスを有効活用

## ベロシティ (Velocity)

### 概要
チームが1スプリントで完了できるストーリーポイントの合計値を示す指標。

### ベロシティの計算

```
スプリント1: 完了したストーリーポイント = 20pt
スプリント2: 完了したストーリーポイント = 25pt
スプリント3: 完了したストーリーポイント = 23pt

平均ベロシティ = (20 + 25 + 23) / 3 ≒ 23pt
```

### ベロシティの安定化

#### 初期段階（1〜3スプリント）
```
スプリント1: 20pt 完了
スプリント2: 30pt 完了
スプリント3: 18pt 完了

→ ベロシティが不安定
→ チームがまだ慣れていない
→ 見積もり精度が低い
```

#### 安定期（4スプリント以降）
```
スプリント4: 24pt 完了
スプリント5: 23pt 完了
スプリント6: 25pt 完了

→ ベロシティが安定してきた
→ 平均 24pt と予測できる
→ 次のスプリント計画に活用
```

### ベロシティの使い方

#### 1. スプリント計画の精度向上
```
過去3スプリントの平均ベロシティ: 24pt
↓
次のスプリントで24pt分のタスクを計画
↓
無理のない現実的な計画が立てられる
```

#### 2. リリース計画の予測
```
残り120ptのバックログ
平均ベロシティ: 24pt/スプリント

→ 5スプリント（約10週間）で完了予測
```

#### 3. チームのキャパシティ把握
```
ベロシティが低下している場合:
- チームメンバーの欠員
- 技術的な問題が発生
- 見積もりが甘かった

→ 早期に問題を発見できる
```

### ベロシティの注意点

#### やってはいけないこと

1. **チーム間でベロシティを比較する**
   ```
   チームAのベロシティ: 30pt
   チームBのベロシティ: 20pt

   → 「チームBは遅い」は間違い
   → ストーリーポイントの基準が違う
   → チームごとの「1pt」が異なる
   ```

2. **ベロシティを個人の評価に使う**
   ```
   ❌ 「ベロシティが高い人が優秀」
   ✅ ベロシティはチーム全体の指標
   ```

3. **ベロシティを無理に上げようとする**
   ```
   ❌ 「ベロシティ30pt目指せ！」
   → 見積もりを甘くするだけ
   → 品質が下がる

   ✅ 自然な改善を待つ
   → プロセス改善でベロシティは自然に向上
   ```

#### 正しい使い方

1. **安定化を待つ**
   - 最初の2-3スプリントは不安定
   - 4スプリント以降で活用
   - 焦らず自然な安定化を待つ

2. **計画の指標として使う**
   - 「次のスプリントで何pt取り込むか」の判断材料
   - 無理のない計画を立てる

3. **改善の効果測定**
   - プロセス改善後にベロシティが向上したか確認
   - ただし短期的な変動は気にしない

### ベロシティとストーリーポイントの関係

```
ストーリーポイント:
- タスクの複雑さを相対評価した値
- チームごとに基準が異なる

ベロシティ:
- 1スプリントで完了したストーリーポイントの合計
- チームのキャパシティの指標
- 安定化することで計画精度が向上

関係:
ベロシティが安定 = チームの見積もり精度が向上
→ より正確なスプリント計画が可能
```

## まとめ：3つの概念の使い分け

| 概念 | 目的 | 使うタイミング | 効果 |
|-----|------|-------------|------|
| **スパイク** | 不確実性を減らす | 見積もり困難な調査が必要な時 | 実装の見積もり精度向上 |
| **タイムボックス** | 時間を区切る | すべての会議・スプリント・調査 | 集中力維持、ダラダラ防止 |
| **ベロシティ** | チームのキャパシティ測定 | 4スプリント以降の安定期 | 現実的な計画立案 |

### 実践例

```
状況: 新しい技術スタックの導入が必要

1. スパイクで調査（タイムボックス: 2日）
   → 実装可能性と見積もりを明確化

2. 調査結果から実装タスクをストーリーポイント化
   → 例: 8pt（過去のベロシティから約3日相当と予測）

3. スプリントプランニングで取り込み判断
   → 平均ベロシティ24pt、今回は8pt消費

4. スプリント完了後、実際の完了ポイントを記録
   → ベロシティの更新と次回計画への反映
```
