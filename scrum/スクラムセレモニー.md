# スクラムのセレモニー（イベント）

## 概要

スクラムフレームワークにおける5つの主要なセレモニー（イベント）についてまとめる。スプリント0の準備事項（DoD/DoR/ストーリーポイント基準/Feature Team vs Component Team）、スプリントプランニング、デイリースクラム、スプリントレビュー、スプリントレトロスペクティブの各セレモニーと、スクラムマスターの実態やスクラム（形式）vs アジャイル（本質）の議論を含む。

---

## スプリント0 (Sprint 0)

### 概要
スクラムを正式に開始する前の**準備期間**。

**重要**: スプリント0は正式なスクラムのセレモニーではなく、実務上よく使われる「準備フェーズ」の呼び名。

### 目的
スクラムを円滑に開始するための基盤を整える。

### 実施内容

#### 1. 環境準備
- 開発環境のセットアップ
- CI/CDパイプラインの構築
- バージョン管理システムの準備
- 開発ツールの選定と導入

#### 2. アーキテクチャ設計
- システムアーキテクチャの基本設計
- 技術スタックの決定
- 設計原則・コーディング規約の策定
- セキュリティ方針の策定

#### 3. プロダクトバックログの準備
- 初期プロダクトバックログの作成
- ユーザーストーリーの洗い出し
- 優先順位の設定
- 見積もり（ストーリーポイント）の実施

#### 4. チーム体制の整備
- ロール（PO、SM、Dev）の確定
- チームルールの策定
- コミュニケーション手段の確立
- 作業場所・時間の調整

#### 5. Definition of Done (DoD) の策定

- 「完了」の定義を明確化
- テスト基準の設定
- コードレビュー基準の設定
- ドキュメント要件の設定

**DoD vs 受け入れ条件 (Acceptance Criteria) の違い**:

| 項目 | Definition of Done (DoD) | 受け入れ条件 (Acceptance Criteria) |
|-----|-------------------------|--------------------------------|
| **スコープ** | チーム全体で共通 | ストーリーごとに個別 |
| **適用範囲** | すべてのストーリー | 特定のストーリーのみ |
| **内容** | プロセス・品質基準 | 機能要件・ビジネス要件 |
| **決定時期** | スプリント0で策定 | ストーリー作成時に定義 |
| **変更頻度** | ほとんど変わらない | ストーリーごとに異なる |

**例**:
- DoD: 「テストカバレッジ80%以上」「コードレビュー完了」← すべてのストーリーに適用
- 受け入れ条件: 「名前で部分一致検索ができる」「検索結果が10件ずつ表示」← このストーリーだけ

**ストーリー完了の判定**:
```
ストーリーが完了 = 受け入れ条件 + DoD
```

**具体例**:
```markdown
## Definition of Done (完了の定義)

ストーリーが「完了」と見なされるためには、以下をすべて満たすこと：

1. コードが実装されている
2. ユニットテストが書かれ、パスしている（カバレッジ80%以上）
3. コードレビューが完了している
4. コーディング規約に準拠している（Linter通過）
5. mainブランチにマージされている
6. 受け入れ条件をすべて満たしている
7. ドキュメントが更新されている（必要な場合）
8. プロダクトオーナーの承認を得ている
```

#### 5-2. Definition of Ready (DoR) の策定
スプリントプランニングでストーリーを取り込むための「着手可能条件」。

**具体例**:
```markdown
## Definition of Ready (着手可能の定義)

ストーリーがスプリントに取り込まれるためには、以下を満たすこと：

1. ユーザーストーリーが明確に記述されている
2. 受け入れ条件（Acceptance Criteria）が定義されている
3. 見積もり（ストーリーポイント）が完了している
4. 依存関係が明確になっている
5. 技術的な実現可能性が確認されている
6. UIモックやデザインが準備されている（必要な場合）
```

#### 5-3. ストーリーポイント「1」の基準策定
相対見積もりの**基準点**となる「1ポイント」を定義する。

**日本語訳**: ストーリーポイント = 「見積もりポイント」「相対見積もり」

**なぜ重要か**:
- すべての見積もりはこの「1」を基準に相対的に決まる
- チーム全員で共通認識を持つことが不可欠
- この基準がブレると見積もり全体が崩れる

**ストーリーポイントと DoD・受け入れ条件の関係**:

```
ストーリーポイント（見積もり）の構成要素:

┌─────────────────────────────────────┐
│ ストーリーポイント = 3pt            │
├─────────────────────────────────────┤
│ 【受け入れ条件の実装】← 変動部分    │
│  - 機能A実装                        │
│  - 機能B実装                        │
│  - 機能C実装                        │
├─────────────────────────────────────┤
│ 【DoD作業】← すべてに共通           │
│  - ユニットテスト作成               │
│  - コードレビュー対応               │
│  - ドキュメント更新                 │
│  ※ 暗黙的に含まれる                │
└─────────────────────────────────────┘
```

**見積もりの考え方**:
- **受け入れ条件**を見て複雑さを判断（メイン）
- **DoD作業**は「当然やる前提」として織り込む（ベースライン）
- 結果として相対的なポイントが決まる

**例**:
- ストーリーA: 受け入れ条件3個、シンプル → 3pt
  - （実装 + テスト + レビュー + ドキュメント すべて含む）
- ストーリーB: 受け入れ条件5個、複雑 → 5pt
  - （実装 + テスト + レビュー + ドキュメント すべて含む）

DoD作業は両方に含まれているが、受け入れ条件の違いで相対的なポイントが変わる

**基準の作り方**:
1. 過去に実装した簡単なストーリーを選ぶ
2. または架空の「典型的な小さいストーリー」を定義
3. チーム全員で「これを1とする」と合意

**具体例**:
```markdown
## ストーリーポイント「1」の基準（ベースラインストーリー）

【1ポイント = 「単純なCRUDのRead実装」】

例: 「ユーザー一覧を取得するAPI」
- 実装時間: 2〜4時間
- 作業内容:
  - Controller: 1つのエンドポイント追加（GET /users）
  - UseCase: 既存Repositoryを呼ぶだけ
  - テスト: 正常系1件、異常系1件
  - 複雑な条件分岐なし
  - 新規テーブル作成なし

他のストーリーはこれと比較して見積もる:
- 2ポイント = 1ポイントの2倍の複雑さ
- 3ポイント = 1ポイントの3倍の複雑さ
- 5ポイント = 1ポイントの5倍の複雑さ
- 8ポイント = 1ポイントの8倍の複雑さ（分割を検討）
```

**フィボナッチ数列の利用**:
多くのチームは `1, 2, 3, 5, 8, 13, 21` を使用。
- 大きい数字ほど不確実性が高いことを反映
- 8以上は分割を検討する目安

#### 5-4. Feature Team vs Component Team

**Feature Team（フィーチャーチーム）= スクラムの理想**:
- **機能（Feature）単位**でエンドツーエンドで開発
- チームは**クロスファンクショナル**（フロント、バック、インフラ全部できる）
- 1つのチームで機能を完結できる
- ストーリーポイントは「複雑さ」の相対評価で「誰がやるか」に依存しない

**Component Team（コンポーネントチーム）= よくある現実**:
- **技術領域（Component）単位**で分かれたチーム
- 例：フロントエンドチーム、バックエンドチーム、DBチーム
- チーム間の連携が必要
- 専門性は高いが、クロスファンクショナルではない

**図解**:
```
【Feature Team - 理想】
┌────────────────────────────┐
│ Team A（製品機能Aを担当）    │
│ - Aさん: フロント・バック可  │
│ - Bさん: フロント・バック可  │
│ - Cさん: フロント・バック可  │
│ → 誰でも何でもできる         │
└────────────────────────────┘

【Component Team - 現実】
┌────────────────────────────┐
│ Frontend Team               │
│ - Aさん: フロント専門       │
│ - Bさん: フロント専門       │
└────────────────────────────┘
┌────────────────────────────┐
│ Backend Team                │
│ - Cさん: バック専門         │
│ - Dさん: バック専門         │
└────────────────────────────┘
→ 機能を作るには両チームの連携が必要
```

**現実の課題**:
```
同じストーリーでも実際の工数が異なる:
- フロントエンド得意な人がReact実装 → 3pt（本来の見積もり）
- バックエンド専門の人がReact実装 → 実質8pt分の時間（不慣れ）

逆も然り:
- バックエンド得意な人がAPI実装 → 3pt
- フロントエンド専門の人がAPI実装 → 実質8pt分の時間
```

**なぜ問題になるか**:
1. ベロシティ（消化ポイント）がブレる
2. スプリント計画が狂う
3. チームの生産性が見えにくくなる

**対処法**:

##### 対処法1: ベロシティで自然調整（スクラムの基本）
```
スプリント1: 20pt計画 → 12pt完了（不慣れな作業多め）
スプリント2: 12pt計画 → 12pt完了（前回の実績から学習）
スプリント3: 15pt計画 → 15pt完了（徐々に改善）
```
→ **数スプリント回せば自然とチームのベロシティが見えてくる**

##### 対処法2: ペアプログラミング・モブプログラミング
- 得意な人と不慣れな人がペアで作業
- スキル転移が起きる
- 見積もり時も「ペアでやる前提」で評価

##### 対処法3: スキルマトリックスの可視化
チームメンバーのスキルレベルを可視化:

| メンバー | フロント | バック | インフラ | DB |
|---------|---------|-------|---------|-----|
| Aさん | 高 | 低 | 低 | 中 |
| Bさん | 低 | 高 | 中 | 高 |
| Cさん | 中 | 中 | 高 | 低 |

→ スプリントプランニング時に「誰がやるか」も考慮して計画

##### 対処法4: T字型人材を育てる（長期戦略）
```
I字型: 1つの専門性のみ（例: フロントのみ）
T字型: 1つの専門性 + 広く浅い知識
π字型: 2つ以上の専門性

理想: チーム全員がT字型以上
```
→ スプリントレトロスペクティブで「スキル習得」をアクションアイテムに

##### 対処法5: 見積もり時の前提を明確化（現実的なアプローチ）
```
プランニングポーカーで見積もる際:
「このストーリー、Aさんがやる前提で見積もる？」
「じゃあAさんなら3pt、でもBさんがやるなら5ptだね」
→ 「Aさんアサイン前提で3pt」と記録
```

**推奨アプローチ（段階的に改善）**:

```
短期（1〜3スプリント）:
→ 対処法3、5を使って現実的に計画

中期（3〜6ヶ月）:
→ 対処法2でスキル転移を進める

長期（6ヶ月〜）:
→ 対処法4でチーム全体のスキルを底上げ
→ 理想的なクロスファンクショナルチームへ
```

**結論**:
スクラムの理想論は「誰でもできる」だが、現実にはスキル差がある。
**ベロシティの自然調整 + 継続的なスキル向上** で徐々に理想に近づけていくのが現実的。

完璧を目指すより、スプリントごとに少しずつ改善していくことが重要。

#### 5-5. Component Team は本当に悪なのか？

**スクラムの教科書**: 「Feature Teamを目指せ！Component Teamはアンチパターン！」

**実務の現実**: 「Component Teamの方が合理的なケースも多い」

##### Component Team のメリット

**1. 専門性の高さ = 品質・生産性の向上**
```
フロント専門チーム:
- UIの細かい作り込みができる
- パフォーマンス最適化が得意
- アクセシビリティ、UXにも配慮できる
- 最新のフロント技術にキャッチアップしやすい

バック専門チーム:
- 複雑なビジネスロジックを書ける
- DB設計・パフォーマンスチューニングが得意
- セキュリティ対策も万全
- スケーラビリティを考慮した設計ができる

結果: 「餅は餅屋」の方が高品質なコードが書ける
```

**2. 技術スタックが複雑すぎる問題**
```
モダンなWebアプリ開発:

フロント:
- React/Vue/Angular
- TypeScript
- CSS-in-JS / Tailwind
- 状態管理（Redux/Zustand/Recoil）
- Webpack/Vite
- Testing Library

バック:
- Scala/Java/Go/Node.js
- ORM（Slick/Hibernate）
- API設計（REST/GraphQL/gRPC）
- 認証・認可（JWT/OAuth）
- DB最適化
- キャッシュ戦略

→ 両方を「プロレベル」で習得するのは非現実的
→ 中途半端にやるより、1つを極めた方が効率的
```

**3. 採用・育成がしやすい**
```
Feature Team向け採用:
「フロントもバックもできるフルスタックエンジニア募集」
→ 候補者が少ない、採用競争が激しい

Component Team向け採用:
「フロントエンドエンジニア募集」
「バックエンドエンジニア募集」
→ 候補者が多い、専門性で評価しやすい
```

**4. チーム間調整コストは許容範囲**
```
調整コストはある。でも:
- Slack/Teams で非同期連携
- 週1回の合同ミーティング
- API仕様書をOpenAPIで明確化
- フロント・バックで別スプリントで動かす

むしろ不慣れな領域で試行錯誤する時間の方が無駄
```

##### Feature Team のデメリット（現実）

```
- T字型人材の育成に時間がかかる（6ヶ月〜1年以上）
- 専門性が薄れる可能性（広く浅くなる）
- 技術の進化についていけない（両方キャッチアップは大変）
- コードレビューが甘くなる（専門外だと見抜けない）
- 採用難易度が上がる
```

##### どちらを選ぶべきか？

**Feature Team が向いているケース**:
- チームが小規模（3〜5人）
- 技術スタックがシンプル
- 長期間同じメンバーで開発する
- 学習意欲が高いメンバーが揃っている
- スタートアップなど柔軟性が最優先

**Component Team が向いているケース**:
- チームが大規模（10人以上）
- 技術スタックが複雑（モダンなWeb開発）
- 高い専門性が求められる
- 短期間で成果を出す必要がある
- 採用市場を考慮する必要がある

##### 現実的な折衷案

**ハイブリッド型**:
```
基本: Component Team
  ↓
特定の機能で: 一時的に Feature Team を編成
  ↓
完了後: Component Team に戻る

例:
「ユーザー認証機能」の開発時だけ、
フロントのAさん + バックのBさんでペア
→ 機能完成後、各チームに戻る
```

**結論（現実的な視点）**:

Feature Team は理想だが、Component Team も全然あり。
むしろ状況によっては Component Team の方が合理的。

重要なのは：
1. チームの状況を正しく理解する
2. 無理に Feature Team を目指さない
3. Component Team でも十分に成果は出せる
4. チーム間の連携を円滑にする仕組みを作る

**「教科書通りにやる」より「チームに合った方法を選ぶ」方が重要。**

#### 6. リリース計画
- 初期リリース計画の策定
- マイルストーンの設定
- 依存関係の洗い出し

### 期間
- 通常 **1〜2週間**
- プロジェクトの規模や複雑さに応じて調整
- 長すぎると本来のスクラムの価値が損なわれる

### 成果物
- セットアップ済みの開発環境
- 初期プロダクトバックログ
- Definition of Done
- チーム体制とルール
- 基本的なアーキテクチャドキュメント

### 注意点

#### やるべきこと
- 最小限の準備に留める
- 実際にコードを書いて動作確認する（Hello World的な実装）
- チームの合意形成を重視

#### やってはいけないこと
- 完璧な設計を目指す（過度な設計）
- 詳細な仕様書を大量に作る
- プロダクトバックログの全項目を詳細化する
- スプリント0を長期化させる

### スプリント0後の流れ

```
スプリント0（準備期間）
  ↓
スプリント1開始
  ↓
[スプリントプランニング]
  ↓
開発開始...
```

### よくある議論

**Q: スプリント0は必須か？**
A: 必須ではない。既存プロジェクトに途中参加する場合や、環境が既に整っている場合は不要。

**Q: スプリント0でどこまで作り込むべきか？**
A: 「スプリント1で価値を届けられる最小限の準備」が目安。作り込みすぎない。

**Q: スプリント0でもデイリースクラムは必要か？**
A: チーム次第。準備作業の進捗共有として実施するチームもある。

## フロントエンド・バックエンド混合チームの問題

### 問題の本質

フロントエンドとバックエンドのエンジニアを1つのスクラムチームに混ぜると、**ストーリーポイントの基準が合わず破綻する**ことが多い。

#### 問題1: 「1ポイント」の基準が合わない

```
フロントエンド開発者の「1pt」:
- 簡単なボタン追加
- CSSアニメーション + 状態管理
- 作業時間: 2時間

バックエンド開発者の「1pt」:
- 簡単なAPI追加
- Controller + UseCase + Repository
- 作業時間: 2時間

同じ「1pt」でも作業内容が全く異なる！
```

#### 問題2: 相対見積もりが機能しない

```
ストーリー: 「ユーザー検索機能」

フロントエンド作業（FE）:
- 検索フォーム実装
- 結果一覧表示（コンポーネント化）
- ページネーション
- ローディング・エラー表示
→ FE開発者「これ5ptくらい」

バックエンド作業（BE）:
- 検索API実装
- DB検索最適化
→ BE開発者「これ3ptじゃない？」

見積もりが合意できない！
```

#### 問題3: ベロシティが意味をなさない

```
スプリント1: バックエンド中心の作業 → 30pt達成
スプリント2: フロントエンド中心の作業 → 20pt達成

「ベロシティが下がった！」
← いや、単に作業内容が違うだけ...
```

### 実務での対策パターン

#### 対策1: チーム分割（推奨）

```
1つの混合チーム（FE+BE）
   → ストーリーポイント基準がブレる

フロントエンドチーム + バックエンドチーム
   → 各チームが独自のストーリーポイント基準を持つ
   → フロントチームの「1pt」とバックチームの「1pt」は別物
```

**メリット**:
- 見積もりの精度が上がる
- ベロシティが安定する
- チーム内で技術的な相談がしやすい

**デメリット**:
- フロント・バック間の調整が必要
- 依存関係の管理が複雑になる

#### 対策2: フィーチャーチーム（機能別チーム）

```
ユーザー管理チーム（FE+BE、ユーザー機能担当）
検索機能チーム（FE+BE、検索機能担当）

同じ機能領域に長期間特化することで、
チーム内で見積もりの共通認識が形成される
```

**メリット**:
- 機能単位で完結できる
- チーム間の依存が減る

**デメリット**:
- 初期は見積もりが安定しない
- ドメイン知識の習得に時間がかかる

#### 対策3: T字型スキル育成（理想だが現実的には困難）

```
全員がフロントもバックもある程度できる
→ 共通の基準で見積もれる

でも現実には:
- 学習コストが高い
- 専門性が薄れる可能性
- 採用が難しい
```

#### 対策4: 別々のポイント制（現実的）

```
同じストーリー内で、FE作業とBE作業を分離:

ストーリー: 「ユーザー検索機能」
- フロントエンド作業: FE-5pt
- バックエンド作業: BE-3pt

別々に見積もって、別々にベロシティを管理
```

**例（JIRAなど）**:
```
Epic: ユーザー検索機能
 ├─ Story (FE): 検索UIの実装 [FE-5pt]
 └─ Story (BE): 検索APIの実装 [BE-3pt]
```

**メリット**:
- 各領域で正確な見積もりができる
- ベロシティが安定する
- 依存関係が明確になる

**デメリット**:
- 管理が複雑になる
- ストーリー分割の粒度調整が必要

#### 対策5: 時間見積もり併用（非推奨）

```
ストーリーポイントを諦めて時間で見積もる
「このストーリーは16時間」

でもこれはスクラムの良さ（相対見積もりの利点）が失われる
```

### スプリント0での決定事項に追加すべきこと

フロント・バック混合チームの場合、スプリント0で以下を明確に決める：

1. **チーム編成方針**
   - 混合チームか？分割か？

2. **見積もり方針**
   - 統一ポイントか？別々のポイントか？

3. **ストーリー分割ルール**
   - FE/BEで別ストーリーにするか？
   - 1つのストーリーにまとめるか？

4. **ベロシティの計測方法**
   - 合算するか？別々に追跡するか？

### まとめ

フロント・バック混合チームでのストーリーポイント統一は**理論上は美しいが、実務では困難**。

**現実的な解決策**:
- チーム分割（FEチーム、BEチーム）
- または別々のポイント制（FE-pt、BE-pt）

**重要**: どの方針を取るにせよ、スプリント0で明確に決めて、チーム全員で合意しておくこと。

## 1. スプリントプランニング (Sprint Planning)

### 概要
スプリントの最初に実施する計画ミーティング。

### 目的
- **何を作るか (What)** を決定する
- **どうやって作るか (How)** を決定する

### 実施内容
1. プロダクトバックログから優先度の高い項目（PBI: Product Backlog Item）を選択
2. スプリントゴールを設定
3. 選択したPBIをタスクに分解してスプリントバックログを作成
4. 各タスクの見積もりを行う

### 時間
- 通常 **2〜8時間**（スプリントの長さに応じて調整）
- 2週間スプリントなら4時間程度が目安

### 参加者
- スクラムマスター
- プロダクトオーナー
- 開発チーム全員

---

## 2. デイリースクラム (Daily Scrum / Stand-up Meeting)

### 概要
毎日同じ時間・同じ場所で実施する短時間のミーティング。

### 目的
- チーム内の情報共有
- 障害の早期発見
- 進捗の可視化

### 実施内容（3つの質問）
各メンバーが以下を共有：
1. **昨日何をしたか** (What did I do yesterday?)
2. **今日何をするか** (What will I do today?)
3. **障害はあるか** (Are there any impediments?)

### 時間
- **15分以内**（厳守）
- タイムボックス化が重要

### 形式
- 立ったまま実施することが多い（Stand-up）
- 長引かないようにするため

### 参加者
- 開発チーム全員（必須）
- スクラムマスター
- プロダクトオーナー（オプション）

### ポイント
- 詳細な議論はデイリースクラム後に別途実施
- 進捗報告ではなく、チーム内の調整が目的

---

## 3. スプリントレビュー (Sprint Review)

### 概要
スプリントの最後に実施する成果物のデモンストレーション。

### 目的
- 完成した成果物（インクリメント）をステークホルダーに見せる
- フィードバックを受け取る
- プロダクトバックログを調整する

### 実施内容
1. スプリントゴールの達成状況を確認
2. 完成した機能のデモを実施
3. ステークホルダーからフィードバックを受け取る
4. 次のスプリントに向けてプロダクトバックログを調整
5. リリース計画の見直し

### 時間
- 通常 **1〜4時間**（スプリントの長さに応じて）
- 2週間スプリントなら2時間程度が目安

### 参加者
- スクラムマスター
- プロダクトオーナー
- 開発チーム全員
- **ステークホルダー**（重要！）

### ポイント
- 動くソフトウェアのデモが必須
- PowerPointでのプレゼンではない
- オープンな議論を促進

---

## 4. スプリントレトロスペクティブ (Sprint Retrospective)

### 概要
スプリントレビューの後に実施する振り返りミーティング。

### 目的
- チームの働き方やプロセスを改善する
- 継続的改善（カイゼン）の実施

### 実施内容
1. **良かったこと (What went well?)** を共有
2. **改善できること (What could be improved?)** を洗い出す
3. **次のスプリントで実施するアクションアイテム** を決定

### 時間
- 通常 **1〜3時間**（スプリートの長さに応じて）
- 2週間スプリントなら1.5時間程度が目安

### 参加者
- スクラムマスター（ファシリテーター）
- 開発チーム全員
- プロダクトオーナー
- **ステークホルダーは参加しない**（チーム内のセーフスペース）

### フォーマット例
- **KPT法**: Keep（続けること）, Problem（問題）, Try（試すこと）
- **星取り法**: 良かった点に星をつける
- **タイムライン**: スプリント中の出来事を時系列で振り返る

### ポイント
- 人ではなくプロセスを改善する
- 具体的なアクションアイテムを決める
- 次のスプリントで実際に試す

---

## 5. スプリント (Sprint)

### 概要
スクラムの基本単位となる**タイムボックス**（固定期間）。

### 期間
- 通常 **1〜4週間**
- 多くのチームは **2週間** を採用

### スプリント内の流れ
```
スプリント開始
  ↓
[スプリントプランニング] ← スプリントの最初
  ↓
[デイリースクラム] ← 毎日実施
  ↓
開発作業
  ↓
[デイリースクラム] ← 毎日実施
  ↓
[スプリントレビュー] ← スプリントの最後
  ↓
[スプリントレトロスペクティブ] ← スプリントの最後
  ↓
スプリント終了
  ↓
次のスプリント開始
```

### スプリント中の原則
- **スプリントゴールは変更しない**
- 期間の延長は認めない
- 品質基準（Definition of Done）は下げない
- スコープは必要に応じて調整可能（プロダクトオーナーと開発チームの合意）

### スプリントの成果物
- **動くソフトウェア（インクリメント）**
- リリース可能な状態であること（Definition of Done を満たす）

---

## セレモニーの時間配分例（2週間スプリント）

| セレモニー | 頻度 | 時間 | 合計時間/スプリント |
|----------|------|------|-------------------|
| スプリントプランニング | 1回 | 4時間 | 4時間 |
| デイリースクラム | 10回 | 15分 | 2.5時間 |
| スプリントレビュー | 1回 | 2時間 | 2時間 |
| スプリントレトロスペクティブ | 1回 | 1.5時間 | 1.5時間 |
| **合計** | - | - | **10時間** |

→ 2週間（80時間）のスプリントで、セレモニーは約 **12.5%** の時間

---

## よくある誤解

### デイリースクラムは進捗報告会
→ チーム内の調整とコラボレーションが目的

### スプリントレビューはQAのためのテスト会
→ ステークホルダーからフィードバックを得るデモ会

### スプリントレトロスペクティブは反省会
→ プロセス改善のための前向きな振り返り

### スプリント中にスコープを変えてはいけない
→ スプリントゴールは守るが、スコープは調整可能

---

## 参考：スクラムの3つのロール

セレモニーに関わる主要なロール：

### プロダクトオーナー (Product Owner)
- プロダクトバックログの管理
- 優先順位の決定
- ステークホルダーとの調整

### スクラムマスター (Scrum Master)
- スクラムプロセスの推進
- 障害の除去
- チームのサポート

### 開発チーム (Development Team)
- 実装作業
- 自己組織化
- クロスファンクショナル

---

## まとめ

スクラムのセレモニーは、透明性・検査・適応という3本柱を実現するための仕組み。

- **スプリントプランニング**: 計画
- **デイリースクラム**: 日々の調整
- **スプリントレビュー**: 成果物の検査
- **スプリントレトロスペクティブ**: プロセスの改善
- **スプリント**: これら全てを包含するタイムボックス

各セレモニーを正しく実施することで、アジャイルな開発が実現できる。

## スクラムマスターの「成功」の裏側 - リアルな話

### 建前：スクラムマスターの役割

スクラムガイドによれば：
- サーバントリーダーシップを発揮
- チームの自己組織化を促進
- 障害を除去してチームを守る
- ファシリテーターとして中立的に進行

### 現実：日本企業でのスクラムマスターの実態

**成功事例の裏で実際にやっていること**:

```
【組織との調整】
- 深夜まで他部署との調整メール
- 理不尽なクレームの矢面に立つ
- 「なぜこのスプリントで完成しないのか」の釈明（毎週）
- 上層部への説明資料作成（スクラム知らない人向けに毎回説明）
- 契約書読んで法務と交渉（固定スコープ契約をどうにか柔軟に）

【チームの盾役】
- ステークホルダーからの突然の要求を防ぐ
- 「優先順位変えてくれ」を何度も断る
- チームメンバーの評価面談で擁護
- 「あいつ使えない」というクレームを受け止める

【雑用全般】
- Confluence/Jira の管理（誰もやらないから）
- 会議の議事録作成（毎回）
- スプリントレビューの資料作成（本来はチームの仕事）
- ベロシティのグラフ作成と分析
- 「スクラムって何？」の説明を100回以上
- リモート会議のファシリテート + 議事録 + チャット監視

【精神的負荷】
- 土日も頭から離れない
- チームの問題を一人で抱え込む
- 「もっと頑張れ」と言われる（上から）
- 「守ってくれない」と言われる（下から）
- 板挟み状態が続く

→ **これ全部やって、ようやく「成功」**
```

### 問題の本質

```
【構造的な問題】
チームの成功 = SMの献身的な働き
           = SMが「奴隷の如く」対応した結果

これは：
- 持続可能じゃない
- 属人化している
- SMが倒れたら終わり
- 組織が変わっていない（SMが緩衝材になってるだけ）
```

### 持続可能なスクラムとは

**本来のスクラム**:
- SMは特定の役割をサポートする
- 組織全体が変わる必要がある
- SMが「奴隷の如く」働く必要はない

**最も重要なこと**:
> SMが燃え尽きたら、チームも組織も何も残らない。
> 自分を守ることは、逃げじゃなく、正しい戦略。

## スクラム（形式） vs アジャイル（本質）

### 根本的な問い：何のためにやるのか？

```
【スクラム = 手段】
- セレモニーを正しくやる
- ストーリーポイントを測定
- ベロシティを追跡
- プランニングポーカー
- レトロスペクティブ

【アジャイル = 目的】
- 素早く価値を届ける
- 変化に対応する
- チームが自律的に動く
- 継続的に改善する
- 顧客に喜ばれる

スクラムはアジャイルを実現する1つの手段に過ぎない
```

### 組織のコミットメントが全て

#### パターンA: ガッチリやる（価値あり）

```
組織がコミット:
- 評価制度を変える
- 予算・契約形態を変える
- 上層部が理解している
- SMに権限がある
- 長期的に継続する

→ ストーリーポイント測定する価値がある
→ ベロシティ追跡する意味がある
→ 投資したコストが回収できる
```

#### パターンB: 中途半端（最悪）

```
組織は変わらない:
- 「スクラムやってみよう」（軽いノリ）
- 評価制度は従来通り
- 契約も縦割り組織も変わらない
- 「とりあえず形だけ」

→ ストーリーポイント測定 = 無駄な作業
→ 仕事が進まない
→ チームは疲弊する
→ 誰も幸せにならない

これが一番ダメ。やらない方がマシ。
```

#### パターンC: やらない（でもアジャイルは目指す）（現実的）

```
形式的なスクラムはやらない:
- セレモニーは最小限
- ストーリーポイント測定しない
- ベロシティ追跡しない

でもアジャイルな働き方は目指す:
- 短いイテレーションで開発
- チームの不平不満を聞く
- 本質的な問題を解決
- 属人化排除などの具体的な目的を設定
- チームの実態に合わせる

→ コストかからない
→ 本質的な改善に集中できる
→ チームは動く
→ 価値は届く
```

### 実利主義のアプローチ（推奨）

#### 1. チームの不平不満を聞く
```
- 定期的に1on1
- 「何が困ってる？」を聞く
- スクラムの形式より、実際の問題を解決

例:
- 「テストが書きにくい」→ 環境改善
- 「レビューが遅い」→ レビュー体制見直し
- 「AさんしかできないことがXXX」→ ドキュメント整備
```

#### 2. Component Team で現実的に
```
- Feature Team を無理に目指さない
- フロント・バックで分ける
- それぞれの専門性を活かす
- 調整コストは受け入れる
```

#### 3. 具体的な目的を設定
```
「スクラムを導入する」ではなく
「属人化を排除する」
「リリースサイクルを2週間にする」
「技術的負債を20%減らす」

→ 測定可能で具体的
→ チームに響く
```

### まとめ：形式より本質

```
重要な問い:
「スクラムをやることが目的か？」
「価値を届けることが目的か？」

答えが後者なら:
- スクラムの形式にこだわらない
- 測定のコストとリターンを考える
- 組織のコミットメントを確認する
- チームの実態に合わせる
- 本質的な問題を解決する

スクラム原理主義 < 現実主義
```

**経験者の結論**:
> 「ガッチリやるのか、やらないのか、まず決める。
> 中途半端が一番ダメ。
> やらないなら測定もしない。コストに見合わない。
> アジャイルが目的、スクラムは手段。」
