# スクラム導入の実践と教訓

## 概要

実際にスクラム導入に関わった実践者の視点から、スクラムの本質、組織との相性、失敗から学ぶことの重要性をまとめたドキュメント。ある組織での導入経験、IPAのアジャイル推進の背景、トップダウン組織での導入リスク、戦略的傍観の正当性などを扱う。

---

## ある組織でのスクラム導入

### 初期導入の経緯

- 2010年代に、ある組織でスクラムを導入した
- 初期メンバーがスクラムマスター資格を取得し、組織に持ち込んだ
- 右も左もわからない状態からスタート

### 初期の取り組み

**厳格なアプローチ**:
- アジャイルコーチを招聘
- チーム合宿の実施
- スクラムの各セレモニーを徹底的に実践

**試行錯誤の例**:
```
1週間スプリントで4日プランニング

→ 明らかにやりすぎ
→ でもこうやって経験を積んで学んでいった
→ 徐々に適切なバランスを見つけていく
```

### その後

**研修の継続**:
- 導入から年月が経っても、社内でアジャイル/スクラム研修が続いた
- 研修の評価も良好だった

**重要なポイント**:
> 「研修が続いている」= 学び続ける文化が根付いている

- 実際の運用はプロジェクトによって様々
- ガッチリスクラムをやっているかは不明
- でも「学び続ける文化」が組織に残っている
- これが本質的に重要

## IPAとアジャイル開発

### IPAとは

**正式名称**: 独立行政法人 情報処理推進機構
**英語名**: Information-technology Promotion Agency, Japan
**略称**: IPA
**設立**: 2004年
**所管**: 経済産業省

### 主な役割

1. **情報セキュリティ対策**
   - 脆弱性情報の収集・発信

2. **デジタル人材の育成**
   - 情報処理技術者試験（国家資格）の実施
   - 未踏事業（天才プログラマの発掘）

3. **デジタル基盤の構築**
   - DX推進
   - ソフトウェアエンジニアリング手法の推進

### IPAのアジャイル関連ドキュメント

#### 2020年2月
**「アジャイルソフトウェア開発宣言の読みとき方」**

**背景**:
- 2017年にIPAが「アジャイル型開発におけるプラクティス活用事例調査」ワーキンググループを設置
- 「アジャイル開発の正しい理解が十分に広がっていない」という課題に対応

**目的**:
- オリジナルのアジャイル宣言（2001年、米国で作成）を日本の文脈で解説
- 「アジャイルの12の原則」を読み解くヒントを提供
- 読者の立場による解釈の違いを最小化

#### 2020年3月
**「情報システム・モデル取引・契約書（アジャイル開発版）」**

**重要性**:
- 従来のウォーターフォール型契約だとアジャイル開発がやりにくい
- アジャイル開発に適した契約書のモデルを提示
- 発注側と受注側の揉め事を防ぐ

**契約の違い**:
```
従来: 「要件定義して、全部作って、納品」（変更は追加費用）
アジャイル版: 「短期イテレーションで開発、柔軟に変更OK」
```

### なぜ国が動き出したのか

```
背景:
- DX（デジタルトランスフォーメーション）推進
- 従来のウォーターフォール開発では変化に対応できない
- でも日本企業は「契約」の壁でアジャイルを導入できない

IPAの狙い:
✅ アジャイルの正しい理解を広める
✅ 契約面での障壁を取り除く
✅ 日本のソフトウェア開発を変革する
```

**時期的な意義**:
- 現場でのスクラム導入（2010年代〜）
- IPAのドキュメント発行（2020年）
- 現場が先行し、国が後から追いかけてきた形

## スクラムの本質：チームの幸福度向上

### 幸福度指標（Happiness Metric）

**提唱者**: ジェフ・サザーランド（スクラムの創始者）

**測定方法**:
- 各スプリントのレトロスペクティブでアンケート
- 1〜5段階でスコアリング

**質問内容**:
1. 自分の仕事についてどう感じたか
2. チームについてどう感じたか
3. 会社についてどう感じたか
4. **どうすればもっと幸福になるか** ← 最重要

### 幸福度と生産性の相関

**ハーバード大学の研究**:
```
幸福度が高い → 生産性が向上
```

**Scrum Inc.の実績**:
```
幸福度指標を導入
↓
ベロシティが500%向上（2011年）
↓
結論: 「幸福度の指標が、業績を予測する最も良い指標」
```

### 実務的なアプローチ：不平不満を聞く

形式的な「幸福度アンケート」にこだわる必要はない。

**実利主義のアプローチ**:
```
✅ 定期的に1on1
✅ 「何が困ってる？」を聞く
✅ スクラムの形式より、実際の問題を解決

例:
- 「テストが書きにくい」→ 環境改善
- 「レビューが遅い」→ レビュー体制見直し
- 「AさんしかできないことがXXX」→ ドキュメント整備
```

**フロー**:
```
不平不満を聞く
↓
改善する
↓
幸福度が上がる
↓
生産性向上
```

### 重要な認識

```
【スクラム = 手段】
- セレモニーを正しくやる
- ストーリーポイントを測定
- ベロシティを追跡

【アジャイル = 目的】
- 素早く価値を届ける
- 変化に対応する
- チームが自律的に動く
- 継続的に改善する
- チームが幸福になる

スクラムはアジャイルを実現する1つの手段に過ぎない
```

**本質**:
> 「スクラムのセレモニーを厳格にやることも大事だったが、
> 本質はチームの幸福度向上」

## トップダウン組織でのスクラム導入の危険性

### よくある失敗パターン

```
トップの期待:
「スクラム導入すれば工数削減できるんでしょ？」
「スケジュール管理しやすくなるんでしょ？」
「コスト下がるんでしょ？」

↓
現場の現実:
- 組織構造は変わらない（トップダウンのまま）
- 評価制度も変わらない
- 契約形態も変わらない
- でもスクラムの「形」だけ導入

↓
結果:
❌ セレモニーの時間で会議が増える
❌ ストーリーポイント測定で工数増える
❌ 「スクラムならどうやるべきか」の議論で時間が消える
❌ スケジュールは予測しにくくなる（最初は不安定）
❌ チームは疲弊する
❌ トップは「効果ないじゃん」と不満

→ 誰も幸せにならない
```

これが「パターンB: 中途半端 ❌最悪」。

### スクラムで工数は「削減できない」

**短期的には工数増える**:
```
+ プランニングポーカー
+ デイリースクラム
+ スプリントレビュー
+ レトロスペクティブ
+ ストーリーポイント測定
= 会議時間が増える
```

**中長期的には改善される（条件付き）**:
```
条件:
✅ チームが自律的に動ける
✅ 継続的改善が実現される
✅ 無駄な作業が排除される
✅ 技術的負債が減る

→ 数ヶ月〜1年後にようやく効果が出る
```

### トップダウン組織との構造的な不一致

```
スクラムの前提:
- チームの自己組織化
- ボトムアップの改善
- プロダクトオーナーへの権限委譲

トップダウン組織の現実:
- 上が決める
- 現場は従う
- 権限は上に集中

→ 根本的に相性が悪い
```

## 失敗から学ぶことの重要性

### 組織の学習サイクル

```
1. トップが「工数削減」目的でスクラム導入
   ↓
2. 形だけ導入、中途半端に実施
   ↓
3. 工数増える、スケジュール不安定、チーム疲弊
   ↓
4. 失敗する
   ↓
5. 「なぜ失敗したのか？」を振り返る（重要！）
   ↓
6. 「目的が間違ってた」「組織が準備できてなかった」
   ↓
7. 次回、正しい理解で再チャレンジ
```

**失敗しないと、組織は学ばない。**

### 成功の弊害

```
もし無理に成功させたら:
- 組織は「スクラムは工数削減ツール」と誤解したまま
- 「頑張ればできる」と証明されてしまう
- 組織構造は変わらない
- また次も同じことを繰り返す
- SMが疲弊する
```

### 失敗の価値

```
失敗すれば:
- 「なぜダメだったのか」を考える機会ができる
- 組織の構造的問題が浮き彫りになる
- 次はもっと良くなる可能性がある
- 誤った理解を修正できる
```

## 戦略的傍観の正当性

### 選択肢3: 傍観（戦略的撤退）

```
✅ 深入りしない
✅ 最低限の役割だけ果たす
✅ 組織が変わるまで待つ
✅ 次の機会に備える

→ 今は時期じゃないと判断
```

### なぜ傍観が正しいのか

**目的がわからない導入は失敗する**:
```
目的が不明確:
- 「工数削減のため」（間違い）
- 「スケジュール管理のため」（間違い）
- 「流行ってるから」（最悪）

正しい目的:
- チームの幸福度向上
- 変化への柔軟な対応
- 継続的な改善
- 価値の早期提供
```

**無理に成功させる必要はない**:
```
経験者が自己犠牲的に働いて成功させる
↓
組織は何も学ばない
↓
経験者は燃え尽きる
↓
次も同じことを繰り返す

→ 持続不可能
```

### 傍観者の役割

```
やること:
✅ 傍観して観察する
✅ 何が起きるか記録する
✅ 聞かれたら答える（押し付けない）
✅ 失敗した後、「なぜ失敗したか」を説明する

やらないこと:
❌ 先回りして全部解決する
❌ 自己犠牲的に働く
❌ 無理やり成功させる
❌ 自分を犠牲にする
```

### 重要な原則

> **「SMが燃え尽きたら、チームも組織も何も残らない。**
> **自分を守ることは、逃げじゃなく、正しい戦略。」**

---

## 導入を止められない場合の対応

### 1. 期待値を下げる（事前に釘を刺す）

```
「スクラムは工数削減ツールじゃないです」
「短期的には会議増えて工数増えます」
「効果が出るまで最低6ヶ月かかります」
「組織構造も変える覚悟ありますか？」

→ ここでNOなら導入すべきじゃない
```

### 2. 最小限で始める（パターンC）

```
❌ ガッチリスクラム（形だけ）
✅ アジャイル的な働き方（本質だけ）

やること:
- 短いイテレーション（1-2週間）
- チームの不平不満を聞く
- 具体的な問題を解決する
- 属人化を排除する

やらないこと:
- ストーリーポイント測定
- プランニングポーカー
- ベロシティ追跡
- 「スクラムならどうやるべきか」議論
```

### 3. 戦略的撤退

```
「今はやらない方がいい」と進言
理由:
- 組織が準備できていない
- 形だけ導入は逆効果
- 失敗すると「スクラムは使えない」という誤解が広まる

→ 時期が来るまで待つ
```

## 実践者からの教訓

### 導入経験からの学び

**初期の厳格なアプローチ**:
- コーチ招聘
- 合宿実施
- 厳格なセレモニー実施
- 1週間スプリントで4日プランニング（やりすぎの例）

**結果**:
- 試行錯誤を通じて学んだ
- 組織にスクラム文化が根付いた
- 研修が続く文化が残った

**代償**:
- 実践者に大きな負荷が集中した
- 同じやり方は繰り返さない

### 重要な気づき

1. **研修が続いていることが大事**
   - 形式的な運用より、学び続ける文化
   - 完璧なスクラムより、継続的改善の姿勢

2. **本質はチームの幸福度向上**
   - セレモニーは手段
   - 目的は価値提供とチームの幸福

3. **失敗も大事**
   - 組織は失敗から学ぶ
   - 無理に成功させる必要はない

4. **自分を守ることも戦略**
   - 燃え尽きたら何も残らない
   - 傍観も正しい選択肢

## まとめ

### スクラム導入の本質

```
❌ 工数削減ツール
❌ スケジュール管理ツール
❌ 生産性向上ツール

✅ チームの幸福度を上げる手段
✅ 変化に対応する働き方
✅ 継続的に改善する文化
✅ 価値を早く届ける仕組み
```

### 組織の準備ができているかの判断基準

```
準備ができている:
✅ チームの自律を認める覚悟がある
✅ 組織構造を変える意思がある
✅ 短期的な工数増を許容できる
✅ 失敗を学びの機会と捉えられる
✅ 長期的視点で投資できる

準備ができていない:
❌ 工数削減が目的
❌ トップダウンを維持したい
❌ すぐに効果を求める
❌ 失敗を許容できない
❌ 形だけ導入したい

→ 準備不足なら「今は時期じゃない」
```

### 実践者の役割

```
初回導入時:
- 厳格に、徹底的にやる
- コーチをつける、学ぶ
- 試行錯誤して経験を積む
- 文化を根付かせる

経験を積んだ後:
- 目的を見極める
- 無理に成功させない
- 失敗から学ぶことを許容
- 自分を守る（戦略的傍観も選択肢）
```

### 最も重要なこと

> **「スクラムは手段、アジャイルが目的、幸福が本質」**

形式に囚われず、本質を見失わないこと。

## アジャイル vs ウォーターフォールの誤解

### よくある誤解

```
❌ アジャイル = ウォーターフォールの対義語
❌ アジャイルにはウォーターフォール的な要素は含まれない
❌ ウォーターフォールは古い、アジャイルは新しい
❌ アジャイルが常に正解
❌ ウォーターフォールは悪
```

この二項対立の構図自体が間違っている。

### アジャイルの本質

```
アジャイルとは:
✅ 変化に対応できる
✅ 柔軟
✅ 継続的改善
✅ 早期のフィードバック
✅ 価値の早期提供

アジャイルの対義語:
❌ 変化に対応できない
❌ 硬直的
❌ 計画変更不可
❌ フィードバックが遅い
❌ リリースが遅い
```

**重要**: ウォーターフォール「手法」自体が悪いわけではない。
問題なのは「硬直的な運用」「変化への対応拒否」。

### 適材適所の考え方 ⭐正解

#### ウォーターフォールが向いている場面

```
✅ 要件が最初から明確
✅ 変更の余地がない（例：法規制対応）
✅ 大規模インフラ構築
✅ ハードウェア開発と連携する案件
✅ 契約上、スコープと納期が固定
✅ 外部ベンダーとの調整が複雑
✅ チームが分散していて頻繁な調整が困難

例:
- 銀行の基幹システム更改
- 医療機器のソフトウェア開発（規制対応必須）
- 公共インフラのシステム構築
- 大規模なデータ移行プロジェクト
```

#### アジャイルが向いている場面

```
✅ 要件が不明確
✅ 市場の変化が激しい
✅ 早期にフィードバックが欲しい
✅ 顧客の要望が変わりやすい
✅ 新規事業・プロダクト開発
✅ UI/UXの試行錯誤が必要
✅ チームが小規模で密に連携できる

例:
- スタートアップの新規サービス開発
- Webアプリケーションの機能追加
- モバイルアプリの継続的改善
- データ分析・AI/ML系のプロジェクト
```

#### ハイブリッドアプローチ

```
✅ 全体計画はウォーターフォール
✅ 各フェーズ内はアジャイル

例:
- 大規模システムの全体設計はウォーターフォール
- 個別機能開発はスクラムで2週間スプリント
- マイルストーンは固定、中身は柔軟に対応
```

### スプリント内のミニウォーターフォール

```
スプリント内の流れ:
計画 → 設計 → 実装 → テスト → レビュー

これは小さなウォーターフォールと言える
```

**つまり**:
- アジャイル開発の中にもウォーターフォール的な要素がある
- 短期間で回すか、長期間で回すかの違い
- 完全に対立する概念ではない

### 実務での判断基準

#### プロジェクト開始時に確認すべきこと

```
Q1: 要件は明確か？
YES → ウォーターフォール寄り
NO → アジャイル寄り

Q2: 途中で変更が入る可能性は？
高い → アジャイル寄り
低い → ウォーターフォール寄り

Q3: 早期にフィードバックが必要か？
必要 → アジャイル寄り
不要 → ウォーターフォール寄り

Q4: チームは密に連携できるか？
できる → アジャイル向き
困難 → ウォーターフォール向き

Q5: 契約形態は？
固定スコープ・納期 → ウォーターフォール寄り
準委任・柔軟な契約 → アジャイル向き
```

### アジャイル原理主義の弊害

```
❌ 「ウォーターフォールは古い」
❌ 「アジャイルじゃないとダメ」
❌ 「全プロジェクトでスクラムをやるべき」

→ これも間違い
→ 適材適所が正解
```

**実例**:
```
ケース1: 医療機器ソフトウェア
- 規制対応で仕様変更不可
- アジャイルは向かない
- ウォーターフォール + 厳格な品質管理が正解

ケース2: 新規Webサービス
- 市場の反応を見ながら開発
- ウォーターフォールは向かない
- アジャイル + MVPアプローチが正解
```

### IPAのスタンス

IPAが「アジャイル開発を推進」しているのは：
- DX時代に対応するため
- 柔軟な開発手法の選択肢を広げるため
- 契約面での障壁を取り除くため

**誤解してはいけないこと**:
```
IPAは「ウォーターフォールを否定」していない
「アジャイル一択」とも言っていない
「適切な場面でアジャイルを選択できるように」している
```

### まとめ：二項対立を超えて

```
重要なのは:
❌ アジャイル vs ウォーターフォール
✅ プロジェクトに最適な手法を選ぶ

判断基準:
✅ 要件の明確さ
✅ 変更の可能性
✅ フィードバックの必要性
✅ チームの状況
✅ 契約形態
✅ 組織の成熟度

結論:
どちらも道具。
状況に応じて使い分ける。
原理主義に陥らない。
```

**実践者の視点**:
> 「スクラムは手段、アジャイルが目的」
>
> さらに言えば：
> 「アジャイルも手段、価値提供が目的」
>
> ウォーターフォールでも価値を届けられるなら、それでいい。
